# Local shared tasks and lists

**23 October 2026 · GROUP-02 · PRD-06 / PRD-13.** The local/test database and BFF implement family task/list commands, coherent paginated reads, conflict detection, retained history and private opaque task-priority references. The account domain/sync boundary, memory reader, real task/list screens, private priority controls and explicit browser conflict recovery are connected. GROUP-02 is locally verified and recorded as REVIEW for hosted acceptance. Cloud provisioning remains pending by the product owner's direction.

## Data and authority

`rise.family_tasks` stores the current title, notes, optional assigned member, starting civil date, optional wall time, selected weekdays, archive state and group revision. An empty weekday array means one occurrence on the chosen date. Repeating tasks begin on that date and use the group's immutable IANA timezone. A viewer's device timezone does not change the occurrence's date. The API takes an explicit civil date; it does not infer it from the server's timezone.

`rise.task_occurrences` identifies each report by group, task and date. A completion captures the task title, notes, assigned member, optional wall time, group timezone and task revision, together with the completing member and database timestamp. Later plan edits and archives preserve those snapshots. A second completion leaves the first actor, time and snapshot intact. Undo clears only the chosen report's completion and retains its row as an explicit correction. Existing completed reports remain correctable after task edits or task archive; fresh completions must match the current active schedule. An archived group remains read-only until its owner restores it.

`rise.shared_lists` owns its name, archive state and revision. `rise.shared_items` owns text, quantity, check state, order and revision. Moving an item specifies its next item or the end of the list; the server maintains contiguous ranks in the same transaction. Removing an item erases its text/quantity/check state and keeps an opaque ID barrier. The removed ID cannot be recycled by a late add or edit. List archive preserves items; restore makes the list writable again.

All four content tables enable and force RLS. Reads require a currently active linked session and membership. All active members can collaborate; group ownership does not grant access to another member's private journey. Cross-group task, list, item and assignee identifiers are rejected. Composite group/member and group/parent foreign keys independently enforce those boundaries.

The BFF and authenticated SQL role have only member-scoped SELECT on these tables. The BFF cannot INSERT, UPDATE or DELETE them directly. One fixed private function, `rise_private.change_shared_content(uuid,integer,jsonb)`, is executable only by the BFF and owned by the existing non-login `rise_group_guard`. It has a fixed empty search path, strict action fields and bounded stored values. Runtime roles cannot assume the guard; the guard cannot read private journeys or provider credentials. Neither ordinary clients nor the push/lifecycle workers can call the mutation function. The lifecycle process uses its separate suppression-only hook.

These rules follow the existing [membership boundary](GROUP-MEMBERSHIP.md), [security policy](../SECURITY.md) and [Supabase RLS documentation](https://supabase.com/docs/guides/database/postgres/row-level-security). No schema is exposed through the Data API.

## Commands, reads and conflicts

All writes use `POST /api/v1/groups/commands` with the existing verified account assertion, immutable operation ID, bounded issue time, expected group revision and discriminated command:

| Commands | Behavior |
| --- | --- |
| `task.create`, `task.edit` | Explicit current plan and active-member assignment |
| `task.complete` | Complete or Undo exactly one dated occurrence |
| `task.archive`, `task.restore` | Preserve reports and change task availability |
| `list.create`, `list.rename`, `list.archive`, `list.restore` | Collaborative list management |
| `item.add`, `item.edit`, `item.check`, `item.move`, `item.remove` | Explicit item content, check state, ordering and removal |

The existing actor lock precedes the group row lock. The mutation rechecks current membership and group status after locking. Content, group revision and the minimal fingerprint/result receipt commit together. Receipt failure rolls everything back. Competing commands with the same expected revision yield one success and one `group_changed` conflict. The original operation remains retryable without renumbering; an explicit review is required before submitting different intent against a newer head. A lost-reply retry returns the exact old receipt without overwriting later work, and still requires current membership. Family actions never write personal records or award habit XP.

`GET /api/v1/groups/:groupId/content` returns one collection: `tasks`, `lists`, `items` or `occurrences`. Items require `parentId` for their list; occurrences require a task `parentId`, a civil `date`, or both. The result includes the verified account, group, group revision, collection, at most 50 rows and an opaque continuation value. Further pages require that revision and cursor. A changed revision returns a conflict; the reader must restart its collection, never combine different heads. Membership, parent availability, revision and rows are read in one database statement snapshot. Responses use `Cache-Control: no-store`.

The route is enabled only for fixed local/test environments, like the membership endpoints. It never imports a guest group or creates a private account profile. Original local simulations and the account's storage format remain unchanged. Real account-selected screens invoke these commands through the existing non-secret group-intent boundary. The separate review entry continues to use its original simulations.

## Private priorities and browser reads

`rise.daily_priorities` now accepts `kind = task` with exactly a group UUID, task UUID and occurrence civil date. The personal priority day remains separate from the group's occurrence date. No shared title, note, assignee, completion or membership is copied into the private account records. The owner/session policies and account-root purge remain in force. There is deliberately no foreign key or cascade to a shared parent: losing access or deleting a group must not erase a person's selected priority or their other choices.

New references require a current active family membership, an active group/task and a date on the current schedule. The BFF verifies them inside the personal command transaction through the narrow `authorize_shared_priorities` capability. Under the existing actor lock, sync batches take sorted shared locks on referenced authorized groups before applying any operation; shared content and membership writes take exclusive locks. This gives a pin and a concurrent removal a single authorized order. The guard gains no access to private priorities, journeys or credentials. Authority is a separate domain argument, never a submitted command context or owner assertion.

Existing selections can be reordered or removed after access is lost. A new group, task or occurrence date requires fresh authorization; removing a reference and later adding it is a new selection. The three-slot and uniqueness rules still apply. Pinning, replacement and removal never complete a task or award habit XP. Conflict review refuses a new unavailable target; it cannot silently renumber the old operation. An already accepted personal receipt can acknowledge the owner's private selection after group removal, but contains no shared content and grants no access to the group. Shared-command receipts continue to require current membership.

Account projection, pull, export and recovery preserve these opaque references. Cache formats 1/2, old priority rows without the three new nullable columns, immutable priority intent fingerprints and previously staged import hashes remain compatible. Validation supplies defaults only for a complete old habit/milestone shape; partial extensions are rejected. Guest import continues to exclude every task reference and cannot upload one directly. An append import preserves already selected account references. Portable exports retain the opaque selection for recovery, without restoring shared access or membership.

`src/groups/content.ts` keeps bounded pages in memory and accepts them only for the selected verified owner, requested collection and one group revision. It invalidates data on revision/access changes, rejects overlapping pages, clears failed reads and fences late success/error replies after a newer request or account change. `GroupClient` additionally checks parent IDs and dates. The provider registers only currently loaded, eligible task references with `WorkspaceSession`; account dispatch refuses a vanished new choice without poisoning the private storage session. Family, Today, task, list and priority screens load their required collections through this reader. Current lists drain coherent 50-row pages; task history offers explicit continuation. A reader version subscription lets another mounted consumer continue pagination after an earlier consumer leaves. No shared content is written to the public service-worker cache.

## Browser flows and recovery

Account-selected family screens retain Tasks/Lists, civil-date navigation, assignment, recurring weekdays, saved-date history and archive/restore. Completed reports display their captured title, notes, assignee and timezone; Undo changes only the selected date. A task archive still allows correction of an existing completion, while a group archive remains read-only. Shared actions award no habit XP. English, Russian and Uzbek Latin use the existing components and color roles; authored text is never translated.

Membership and content refresh every 15 seconds while visible, and on focus, visibility and online events. A changed group revision invalidates all affected pages. After a transient unavailable read, fresh successful membership metadata also permits a new first-page read at the same revision. Busy/receipt updates do not trigger retries; successful and in-flight content remains intact. Authority errors are not cleared by this rule, and account/membership fences still apply. Delayed or failed occurrence reads do not show a falsely unchecked task. An absent task/list is reported only after its entire collection loads; a later page still in flight remains loading. Item ordering is disabled until the coherent item collection finishes. Losing membership hides current shared content; it does not erase the user's private priorities or pending recovery intent.

Task, list and item forms save durable drafts through the selected `WorkspaceSession`. Each draft captures its entity ID and reviewed group revision. Submission records one immutable operation before sending. A lost reply retries the same body/ID, including after reload. Receipt acknowledgment clears only the matching draft; newer text or a newer reviewed revision survives. An accepted item add receives a new draft ID for the next item. Save success and navigation wait for receipt acknowledgment and durable cleanup. The form owner remains mounted across its own refresh, but account changes or lost access fence late callbacks and hide the body.

Private priority synchronization can overlap shared-draft saves and receipt cleanup. The account session serializes its cache transactions so those local operations do not falsely conflict with its own acknowledgment or pull. A real change from another tab still fails the strict cache comparison and retains unsaved intent. See [the account cache contract](ACCOUNT-SYNC.md#command-acknowledgment-and-pull-protocol).

A conflict retains the submitted operation. The user can retry it or explicitly stop that pending change, inspect current saved fields and select **Use this version for my edits** before resubmission. This is an explicit new intent; neither the client nor server silently renumbers an old operation. Removed members cannot retry a queued shared write successfully. Recovery remains accessible without displaying the lost group's content.

Task detail can pin/unpin an opaque occurrence reference on the viewer's personal Today. A fourth choice opens the existing ordered priority picker with the candidate visible; the user removes a selection before adding it. Replacement never completes or deletes the underlying task. Unavailable selections remain removable, and unrelated priorities remain intact. The group occurrence date and personal priority date are independent.

## Limits and lifecycle

The private operator configuration defaults to 500 tasks and 100 lists per group, 1,000 retained item IDs per list and 20,000 reported dates per task. Archived records and item barriers count toward limits. `shared_limit` is a recoverable refusal, not silent truncation or deletion. Group writes also consume the existing account mutation quota. GROUP-04 adds [optional notification frequency/retention controls](GROUP-NOTIFICATIONS.md). Production capacity remains QUALITY-03 work.

Auth identities and nicknames are not copied into task or occurrence records. Actor and assignee references use the stable group membership ID. Existing account-suppression and terminal-purge hooks scrub that member's user ID and nickname while preserving group-owned content for remaining members. A former actor is therefore rendered from deidentified membership, never a retained private profile. Deleting a group cascades tasks, occurrence snapshots, lists and item barriers. The readiness hook now recognizes this family integration; GROUP-03 now supplies [authored squad post/reaction/preview erasure](SQUAD-SNAPSHOTS.md), and GROUP-04 supplies [recipient/source notification-job cleanup](GROUP-NOTIFICATIONS.md); future unintegrated tables still fail closed. See [account lifecycle](ACCOUNT-LIFECYCLE.md). [GROUP-05](GROUP-LIFECYCLE.md) now verifies the combined local browser/cache/export/deletion/server-backup replay path; hosted operations and physical-device acceptance remain pending.

## Migration and rollback

`20261023145156_shared_family_content.sql` is additive and is applied after the three membership migrations. It adds four forced-RLS content tables, private limits, the narrow mutation function, receipt command kinds and the family lifecycle readiness integration. `20261023152154_shared_task_priorities.sql` adds three nullable priority columns, the exact reference constraint/uniqueness rule and the two narrow lock/authorization functions. Both are applied on local/test. Cache formats and prior migrations remain unchanged.

Roll back application exposure by disabling the shared-content route/commands while keeping data, receipts, barriers and lifecycle hooks. Do not drop the tables, rewrite applied migrations, reuse removed IDs or remove the suppression ledger. An older lifecycle readiness implementation will refuse purge while these tables exist; deploy the compatible hook and worker together. Preserve pending group drafts before any intentional cache cleanup. Local numbered migration copies encountered during setup were retained privately outside the active migration directory; neither migration history nor database volumes were reset.

After task priorities exist, keep their compatible account reader even if new pin controls are disabled. A pre-extension writer cannot preserve those rows; do not deploy it against populated accounts or drop the new columns as rollback. Existing opaque selections must remain readable and removable, and pending private operations/recovery sources must be retained.
