# Local group membership boundary

**23 October 2026 · GROUP-01 / PRD-14 / SEC-01.** The local/test database, BFF and browser now implement real group membership, invitation and ownership operations. The authorized family task/list backend, private priority references and memory reader are implemented in [GROUP-02](SHARED-CONTENT.md); task/list and priority controls are locally verified. [Exact squad snapshots](SQUAD-SNAPSHOTS.md) are locally verified; [optional group notifications](GROUP-NOTIFICATIONS.md) are now implemented locally with separate group/device consent. The original local simulations and saved profiles are preserved separately. This guide does not claim complete real collaboration or a hosted release. Cloud provisioning remains pending.

## Data and authority

`rise.groups` owns kind, shared name, planning timezone, archive state, revision and the owner account. `rise.memberships` owns a stable member ID, an explicit shared nickname and current status. A group role is derived from the single `owner_id`; it is not duplicated in JWT metadata or a mutable client role. A deferred composite foreign key requires that owner to have an active membership at commit. Transfer and group creation cannot commit an orphan.

`rise.group_preferences` contains only each member's mute and quiet-hour choices. These preferences do not grant push permission or schedule notifications. `rise.group_invitations` contains a SHA-256 token hash, group/creator, creation/expiry and consumption/revocation metadata. `rise.group_receipts` contains an owner-bound request fingerprint and minimal accepted outcome, without authored text or invitation tokens. Group IDs in receipts deliberately survive group deletion for retry acknowledgment.

Every table enables and forces RLS. The BFF has read access subject to current membership and has no general write access to groups, members, preferences or invitations. Ordinary authenticated SQL readers have only minimal group/member and their own preference access; no Data API schema is exposed. The API returns shared nicknames, opaque member IDs, roles, current group fields and the caller's preferences. It does not return member email, private profile names, provider credentials, habits, prayers or pause data. Reading groups never initializes or imports a private journey.

Private fixed database operations are owned by `rise_group_guard`, a non-login, non-inheriting, non-bypass-RLS role. Its capabilities are limited to group tables, rate counters/configuration, the existing active-session predicate, recent-auth metadata and suppression identifiers. It cannot read private journeys or provider-token ciphertext. All functions have an empty search path; PUBLIC, anonymous and service-role execution is revoked. No runtime login can become the guard. The managed Auth schema does not delegate its usage grant to the migration role; `group_actor()` binds the existing identity function during parsing and grants no Auth-table access. A follow-up migration asserts the required predicate/execution grants rather than relying on a silent no-op GRANT.

## Local API

All mutations require the existing verified session, exact Origin and CSRF boundary. Routes reject hosted environments until their release integration is accepted.

| Route | Behavior |
| --- | --- |
| `GET /api/v1/groups` | Current authorized group/member projection and own preferences; no-store response |
| `POST /api/v1/groups/commands` | Strict discriminated command with expected account, immutable operation ID, captured issue time and group revision |
| `POST /api/v1/groups/invitations/preview` | Signed-in, rate-limited token lookup returning only group ID/name/kind/timezone and expiry |
| `POST /api/v1/groups/receipt` | Owner-bound recovery lookup by original operation ID, with current membership rechecked; no invitation token/link |

Commands are `group.create`, `rename`, `archive`, `restore`, `leave`, `delete`, `invite`, `revoke`, `transfer`, `remove`, `preferences` and `accept`. See [the runtime contract](../src/contracts/groups.ts) and [repository](../server/groups/repository.ts).

## Browser state and recovery

The production local/test entry uses `src/groups/` after explicit selection of a verified account journey. Signing in does not import or relabel guest groups. The review build retains its fictional collaboration flows; original local data remains in its existing storage and backup. Real group screens expose membership controls now, with shared content assigned to the following tasks.

`GroupSession` owns current group views, command dispatch, captured revisions and retry state. It validates responses and fences both success and failure after an account change. Server views stay in memory and refresh on focus, visibility, connectivity and a 15-second visible-page interval. A failed authorization/read removes the displayed group view; server authorization is checked on every operation regardless of what a page previously displayed.

Non-secret immutable commands are acknowledged by the existing account store before POST. One unresolved command per account blocks starting another. A remembered account uses its existing owner-scoped IndexedDB draft; a session-only account uses memory. There is no second group cache or cache-format change. These drafts do not enter personal sync operations or portable backups. Private recovery exports may include the pending non-secret command, as advertised by the existing recovery UI. Logout and session-only departure/update safeguards include unresolved group intent, without blocking personal-sync or push-readiness calculations.

Invitation tokens are consumed from initial or same-document URL fragments and removed with `replaceState`. A signed-out visitor gets the account gate and returns to explicit invitation review after account selection. Tokens, received group content and generated invitation links stay in memory. Copy/share needs a user gesture and reports clipboard failure truthfully. Account changes dismiss private forms and clear transient secrets. Joining stores only owner, operation and group IDs durably; after a reload the receipt endpoint checks whether that exact operation succeeded. An unknown receipt requires the original link and another explicit review, never automatic acceptance.

Lost replies replay the same operation ID, issue time, revision and body. Server acceptance followed by failed local cleanup keeps a recoverable pending state. Matching form drafts are cleared only if they still describe the accepted operation; unrelated or newer drafts remain. A stale revision keeps the edit, requires stopping the old operation, and offers an explicit choice to use the newly reviewed group version. Stopping a pending local action never reverses server effects already accepted.

All group copy is available in English, Russian and Uzbek Latin. Existing action/text tokens, controls, sheets and typography remain. Group headers grow for enlarged text; nested sheets restore keyboard focus to their opener. The account deletion ownership error opens group management so an owner can transfer or explicitly delete before retrying account deletion.

The later [bounded invitation increment](GROUP-INVITATIONS.md) returns 20 owner-only metadata rows per page and enforces a configurable retained-history cap. Local acceptance includes 100,000 retained entries with cleanup stopped. The explicit group notification choice starts off; mute alone is not consent. Saving preferences never requests device permission. Receiving also requires separate explicit installation consent, as described in [group notifications](GROUP-NOTIFICATIONS.md).

Create captures an explicit shared nickname and group timezone; it does not copy the private account name. The timezone is immutable at this boundary. Rename and administrative operations require the current owner. Transfer and explicit group deletion require server-clock authentication within ten minutes. A member can leave; an owner must transfer or explicitly delete the group first. Archived shared content and administration are read-only until owner restoration. Leaving and changing one's own delivery preferences remain available for privacy. Archiving or transferring revokes outstanding invitations; restoring does not reactivate them.

Commands serialize first on the acting account's existing personal lock and then on the group row. Transfers never lock a second account after locking the group. Account deletion locks its actor and affected groups in sorted order; transfer into a concurrently deleting member either wins and blocks deletion as ownership, or loses after membership is removed. No accepted operation grants an already-suppressed identity access.

The mutation, revision and receipt share the verified session transaction. Changed reuse of an operation ID returns a conflict. A retained exact retry acknowledges the original outcome after current authorization is checked; invitation recovery additionally requires current ownership and a still-valid original token. Minimal leave/delete receipts remain readable by their actor after departure. Replaying a previously accepted join after removal does not restore membership. Unknown operations more than seven days old or over five minutes in the future require a new explicit decision. The issue time is bounded personal intent, never an authentication or expiry clock. Receipt pruning is owner-only, older than 90 days and bounded to 200 per successful action; the age guard prevents recreation after retention. Current receipts cannot be changed or deleted by the BFF.

## Invitations and abuse controls

An invitation is single-use and expires after seven days by database time. The server generates a 256-bit HMAC token using an HKDF key dedicated to invitations, bound to installation, actor, group and immutable operation ID. This permits recovery after a lost reply without storing a plaintext token. Only its hash enters the invitation table. The returned link places the token in the URL fragment. No server operation sends it to another person.

The browser consumes and removes that fragment before application navigation, keeps the secret out of durable drafts/caches/exports, and requires explicit confirmation naming the group. Copy and share are available only through the user's gesture; a failed clipboard operation displays a localized error. This local implementation does not send invitations itself.

Preview grants no membership. Acceptance locks the group and invitation, rechecks active session, expiry, archive, revocation and consumption, then commits membership and single-use consumption together. An invitation created before a member's departure cannot rejoin that member; an owner must create a fresh invitation. Existing downloaded information cannot be recalled, but every subsequent fetch and commit rechecks current membership.

After an encryption-master-key rotation, already shared links retain their stored hash and original expiry/revocation rules. The server cannot reconstruct an old token using the new key. A create retry refuses to substitute a new token; the owner can revoke the old invitation and explicitly create another. This boundary does not change or rotate any existing installation keys.

Operator-owned `rise_private.group_limits` currently defaults to 50 active memberships per account (including archived groups), 100 active members per group, ten group creations per day, ten invitations per hour, 10,000 retained invitations per group, 60 invitation lookups/acceptance attempts per hour and 200 other changes per hour. They are abuse controls, not commercial tiers. Counters use database time and account locks. Invalid token attempts commit their quota charge even when the action fails. Expired counters are removed in bounded batches during actor activity. GROUP-04 adds [bounded optional message frequency and retention](GROUP-NOTIFICATIONS.md); the existing authenticated account and session/IP protections remain in place.

The isolated sender's existing tick also invokes `prune_group_invitations(200)`. It can delete at most 500 explicitly requested expired candidates, using row locks with `SKIP LOCKED`, after seven days beyond first consumption, revocation or expiry. It cannot read group/invitation rows or change membership. A stopped sender means retention cleanup is delayed; hosted scheduling/monitoring remains an operating gate. Invitations cannot be recovered by recreating a pruned receipt's token.

## Account suppression and restore

Before inserting the deletion ledger, `prepare_group_deletion()` locks all affected groups, refuses every owned group (including archived ones), removes personal preference rows and scrubs the departing account's membership name/identity. The stable deidentified member row is retained for later group-owned history references. A restrictive ledger policy independently prevents suppression before ownership/membership resolution. Failure at the subsequent ledger write rolls the group changes back.

The isolated lifecycle worker performs terminal group cleanup on a separate committed database connection **before** managed Auth deletion. Holding group locks across the provider's separate deletion connection would deadlock. The retained suppression ledger already rejects fresh writes. If a restored backup contains pre-transfer ownership for a suppressed account, the terminal hook removes that obsolete owned group; it does not reactivate the owner. Remaining member identities are scrubbed before provider completion. A failed provider purge leaves suppression and retry work intact; the 35-day retention clock still begins only after verified primary purge. The hook requires a retained ledger and is executable only by the lifecycle role, never by the BFF or sender.

`deletion_integrations_ready()` now recognizes the [GROUP-02 family integration](SHARED-CONTENT.md): tasks, occurrence snapshots, lists and item barriers are group-owned, and actor/assignee references use stable deidentified member IDs. GROUP-03 now includes authored squad post/reaction/preview erasure before suppression and during terminal backup replay. GROUP-04 now erases recipient/source-author `notification_jobs` before suppression and during terminal replay; a missing named cleanup hook still blocks deletion. [GROUP-05](GROUP-LIFECYCLE.md) now verifies the combined local membership/export/cache/deletion/server-backup replay path; hosted and physical-device gates remain pending. Portable private backups cannot recreate real group membership.
