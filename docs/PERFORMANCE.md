# Performance, resilience and capacity

QUALITY-03 measures NFR-01–05 and NFR-07 without changing the existing product, design or saved-data semantics. Cloud provisioning remains pending. Desktop loopback measurements are diagnostics; they cannot certify physical mobile Web Vitals, hosted 100-user capacity, monthly availability or backup recovery targets.

## Reproducible local workload

`tests/support/capacity.ts` creates synthetic data for 100 daily habits and 730 dated occurrences per habit. Historical snapshots are retained independently of current habit versions. The profile is about 10.75 MB; it contains no exported user data. Optional smaller dimensions support focused ordering tests, not a substitute for the required dense workload.

Build and check first, then run the opt-in measurements alone:

~~~sh
npm run check
npx playwright test --config playwright.performance.config.ts
npx playwright test --config playwright.performance-production.config.ts
~~~

The performance configuration reuses the isolated 4180 review origin and the shared request guard, with one worker. Each engine gets a fresh disposable context. The real IndexedDB adapter initializes the profile without placing a large legacy JSON value into localStorage. The test dispatches explicit check, Undo and draft commands through `DeviceSession`, waits for durable acknowledgment, then reopens the database and compares the complete state and revision. The original recovery source remains unchanged. Never point this fixture at 4173, a saved browser profile, a hosted origin or a real account.

Measurements include synchronous dispatch duration, the next animation-frame opportunity, time to durable acknowledgment and startup. The frame opportunity is not a rendered UI-feedback or INP measurement. Three samples per action are an initial discovery set, not a reliable p95 acceptance run. Preserve all engine results and failures, along with source/build hashes, before drawing conclusions.

The repository probe separates read/validation, reducer work, validation/write/clone and work outside the adapter. It retains the real strict IndexedDB transaction and verifies exact replay without an extra revision. The production probe runs separately on 4181, which must not overlap production-entry or PWA tests. It seeds only a fresh disposable context, reloads through production validation, then clicks a real Today habit. It measures the completed DOM state, a subsequent frame opportunity and the saved status, and checks all historical records and XP after reload. It asserts that no reviewer controls are present. These are local diagnostic timings, not physical paint or standardized INP measurements.

Node probes separately measure validation, parsing, account projection/reconstruction and a pure domain check. They establish where CPU work occurs, not network, browser rendering or database latency. Current work and exact scopes are in [the performance evidence](evidence/performance-2026-10-24/README.md).

Group screen code is deferred until its sheet opens; Today rows remain immediately available. Bundle comparisons must use the same build and compression method. The real worker still precaches every public chunk, so initial entry savings do not establish reduced total offline download or faster mobile Web Vitals. Validate failed-download retry, close-during-load focus, cold offline access and unchanged loaded-screen visuals whenever this boundary changes.

## Account burst diagnostic

Run `node --import tsx scripts/infra/check-account-load.ts smoke` first, then `node --import tsx scripts/infra/check-account-load.ts full`, separately from database/browser suites. The fixed test installation must already be running. Full mode creates 100 authorized synthetic accounts with 7,300,000 total habit occurrences; it requires 12 GiB free host disk before starting. A database advisory lock rejects overlapping capacity runs. It does not stop other installations or prevent unrelated test commands, so the operator must reserve the test database.

Administrative access only seeds and removes this run's fixtures. Setup is excluded from request latency and does not measure the import API. Every measured request uses real local Auth, the restricted BFF connection, verified actor, RLS and unchanged production pool/timeouts. Fastify's injected transport excludes network/browser/hosted latency. Each account has a distinct synthetic loopback client address. The workload sends a simultaneous full-check wave, recovers rejected requests with the identical operation ID/body, verifies replay receipts, then repeats for Undo. First-attempt successes, failures and accepted p95 are reported separately from sequential recovery. Every account is read back and compared with every original relational value, ignoring row order only; XP and revisions must match.

The JSON report goes to stdout and `.rise-infra/test/capacity/<run-id>/report.json`. The protected sibling `fixtures.json` records only this run's installation ID, exact synthetic emails and (for mixed mode) exact group IDs/owners for crash recovery; neither file contains auth credentials. Normal completion, assertion failure and handled SIGINT/SIGTERM remove only the registered groups matching their generated owners, then those exact accounts, and verify their group/occurrence rows are gone. A hard process kill cannot run cleanup: inspect the protected manifest against the fixed test installation before removing those exact owner-matched groups and performing exact-email cleanup; never sweep other synthetic users or remove the lifecycle ledger. No guest or other-owner browser data is touched. A nonzero exit may mean a measured capacity shortfall even when recovery and cleanup pass; preserve the report.

This two-wave burst is a local personal-command stress diagnostic. It does not establish the full NFR-03 mixed workload, shared convergence, sustained throughput, physical-device performance or hosted staging acceptance.

## Account mixed diagnostic

Run `node --import tsx scripts/infra/check-account-load.ts mixed-smoke`, then `node --import tsx scripts/infra/check-account-load.ts mixed`, separately from all other database/browser suites. The smaller mode has two accounts and one family; full mixed mode has 100 accounts with the same 100-habit/two-year histories, arranged into 50 explicitly joined synthetic families. It shares the burst diagnostic's fixed-test boundary, advisory lock, disk guard, private manifest, unchanged roles/pool/timeouts and exact cleanup.

Four 30-second rounds schedule one personal mutation per account and one shared dated completion/Undo per family per round: 400 personal and 200 shared mutations. Full/Undo alternate so final personal history and XP can be compared with the original fixture. Arrivals are spread within each round; both request latency and scheduling lateness are recorded. The gate includes lateness in accepted p95, and failed/deferred intentions remain separate rather than disappearing from the report.

All accounts refresh group metadata every 15 seconds. The diagnostic uses the actual `SharedContent` reader and real API responses for content invalidation, errors and dated occurrence reads; a small metadata adapter retains the session's version fencing. Successful shared mutations immediately refresh their actor. The other member's observed state is timed from server acknowledgment. Missing observations and observations beyond 15 seconds fail convergence. This is API/client-state convergence, not browser paint or physical-device acceptance. The tool does not read another member's private account history.

Operation IDs/bodies/revisions are captured before submission. A failed prior command blocks later intentions for that same account/group; deferred intentions are reported. After measurement, the original sequences are recovered with exact IDs/bodies, all receipts replayed, every personal history/XP read back, and both members' final shared snapshots compared. Exact synthetic group IDs and owners are registered before creation; cleanup removes those groups before their accounts. Invitation tokens and credentials never enter reports or manifests. Handled interruption drains outstanding work before cleanup; a hard kill still requires exact manifest recovery.

The 24 October 2026 local run **fails capacity and convergence**. Of 600 planned intentions, 359 first attempts succeeded, 65 returned HTTP 503 and 176 were deferred. Accepted personal/shared p95 including scheduling lateness was 5,348.9/4,936.7 ms. Of 110 accepted shared updates, 94 were observed; 13 exceeded 15 seconds and 16 remained unobserved. All 241 failed/deferred intentions subsequently recovered, exact receipts and complete histories/shared snapshots matched, and cleanup passed. [The full evidence](evidence/performance-2026-10-24/increment-08/README.md) retains all failures and scope limits. No application or timeout change was made for this diagnostic.

The two cross-layer load diagnostic files are checked by `tsconfig.tools.json`, whose existing DOM types cover the actual shared reader's browser type graph. They are excluded only from the Node-only server configuration; production server type coverage is unchanged. `npm run check` still includes both configurations.

A subsequent [BFF-thread experiment](evidence/performance-2026-10-24/bff-thread-discovery/README.md) retains five total database connections and raises first-attempt acceptance to 582/600. Personal/shared scheduled p95 still fails at 4,513.9/3,872.0 ms, and 31 accepted shared updates are late or missing. Every exact replay/history/XP/shared snapshot and cleanup check passes. No production threading architecture or polling change is adopted from this test-only routing experiment.

## Preserve correctness while optimizing

Unknown JSON still receives the same size, depth, record-count, prototype, accessor, field, date and reference checks. Parsing must not silently truncate history or drop unknown safe extensions. A descriptor walk may reduce allocations but must never invoke a getter. Account reconstruction must retain per-parent ordering, explicit prayer records, snapshots and retired-milestone behavior.

Only fresh values produced inside `parseJson` may use its private data-property traversal; arbitrary object inputs retain descriptor checks. This distinction does not make imported content trusted or skip its bounds/schema/reference validation. Stored-profile parsing does not normalize values, so a validated command result can reuse its original JSON text for no-op comparison. Preserve exact output, original recovery data and zero additional receipts/revisions for no-op actions when changing this path.

Local commands keep stable identity, revision conflict handling, atomic state/receipt commits and durable save/error semantics. A faster optimistic UI must not claim that an unsuccessful write was saved. Do not bypass current session/owner checks, cancellation locks, replay receipts, quota recovery or deleted-owner barriers to improve a benchmark.

The account writer uses a direct comparison only for validated relational JSON when finding changed rows. Preserve object-key-order independence, ordered arrays, missing-versus-null fields and scalar types. Keep canonical row keys, import hashes, causal fingerprints and receipt identity unchanged. Verify no-op commands retain every unaffected row revision and removal barrier, and real edits update only their affected records, through the real database/API boundary. For occurrence histories with equal lengths and matching ordered keys, compare every value and build maps only for changed pairs. Identity/length mismatches must use the general path. Preserve insertion/removal, row reindexing and exact SQL/receipt/barrier outcomes, including an old correction replay after later removal.

The dense occurrence read selects its fixed UUID/integer/text/JSON fields directly and preserves the date through `to_json`. Do not let the database driver's native date parser turn civil dates into process-local instants. Keep table-qualified ordering, the owner predicate, aggregate 250,000-record bound and full hydration/output validation. Compare values under alternate SQL date formats and process timezones, test unrelated-owner denial and malformed stored fields, and verify complete history/replay before accepting a read optimization.

The [direct occurrence-read increment](evidence/performance-2026-10-24/increment-09/README.md) verifies faster isolated reads and date/owner/value parity. The identical single-thread mixed workload accepts 377/600 first intentions, with 66 HTTP failures and 157 deferred. Accepted personal/shared scheduled p95 is 5,631.2/4,913.1 ms. Of 121 accepted shared updates, 10 observations are late and 23 remain missing. All 223 failed/deferred intentions recover exactly; every history/XP/shared snapshot and cleanup check passes. Its diagnostic result does not close NFR-03.

The [ordered occurrence-writer increment](evidence/performance-2026-10-24/increment-10/README.md) verifies less map/key CPU work with unchanged SQL and correction barriers. The unchanged mixed workload accepts 542/600 first intentions, with 20 HTTP failures and 38 deferred. Accepted personal/shared scheduled p95 is 4,715.8/4,599.1 ms. Of 177 accepted shared updates, 25 observations exceed 15 seconds and 11 remain missing. All 58 failed/deferred intentions recover exactly; complete histories, XP, shared snapshots and cleanup pass. It does not close the broader QUALITY-03 requirements.
