# Bounded owner invitation history

**24 October 2026 · GROUP-04 increment / PRD-14.** Owner invitation pages and retained-history limits are locally verified. [Optional group notification integration](GROUP-NOTIFICATIONS.md) is now implemented locally; hosted acceptance and cloud provisioning remain pending. [Local evidence](evidence/group-invitations-2026-10-24/README.md).

## Read and browser boundary

`GET /api/v1/groups` includes at most 20 newest invitation metadata rows per owned group, ordered by expiry and UUID descending, plus `invitationNext`. Other members receive an empty invitation list. `GET /api/v1/groups/:groupId/invitations` reads another 20-row page; a continuation requires both its opaque UUID cursor and the observed group revision. The cursor resolves its stored timestamp inside the same SQL statement as current ownership, revision and page reads, retaining Postgres microsecond precision. A changed revision or pruned anchor requires a reload. Unknown query fields are rejected; responses are no-store and contain no token, token hash, email or Auth user ID.

`GroupInvitations` retains one displayed page and opaque back-navigation cursors in memory. Role, account and revision changes discard stale responses. Failed continuation hides old invitation actions and offers an explicit reload. After a transient unavailable read, fresh successful owner metadata restores its authorized first page and resets old navigation. Busy/receipt updates do not clear the error, and authorization errors are not automatically cleared. Keyboard navigation focuses the invitation heading. Revoke confirmation retains the selected revision rather than silently adopting a newer one. A newly created link is available only while its current active metadata is on the loaded page; no link is reconstructed from history. Durable operations, exact receipt replay and invitation-secret handling remain as documented in [membership](GROUP-MEMBERSHIP.md).

## Capacity and authorization

The operator-only `invitations_per_group` limit defaults to 10,000 and permits 1–100,000 retained rows. Creation checks capacity while holding the existing actor and group locks. A full history returns localized `invitation_limit` feedback without changing the group revision or recording success. Bounded cleanup removes expired/revoked/used metadata under the existing seven-day retention policy; a stopped worker may leave new creation blocked, while pages remain readable. Cleanup is not performed inside a failing creation transaction, where it would roll back with the capacity error. After cleanup, the original unaccepted operation can retry with the same identity and body.

Transfer and archive revoke only unconsumed, unrevoked invitations whose expiry is still in the future at the transaction's database clock. Expired, consumed and previously revoked rows keep their terminal metadata and original retention timestamps. Explicit per-link revoke remains unchanged. The actor/group locks, owner checks, recent authentication for transfer, revision update and immutable receipt transaction are unchanged. Acceptance rechecks expiry using `clock_timestamp()` after acquiring the existing group and invitation locks, so a transaction that started before expiry cannot revive a skipped historical link after transfer or archive/restoration. Audit timestamps still use the existing transaction clock. An archived link remains revoked after restoration. This avoids rewriting up to 100,000 retained historical rows when only the outstanding links need revocation. See the [25 October CI regression evidence](evidence/ci-2026-10-25/GROUP-INVITATIONS.md).

Existing invitation frequency limits remain: ten per hour by default, configurable through 100. An accepted exact retry does not consume a new invitation or frequency slot. These are abuse controls, not paid tiers.

Both additive migrations preserve forced RLS, current-session membership and owner-only access. `invitation_read` selects the caller's current owned groups through the existing `rise.groups` policy, then filters invitation rows against that set. This avoids repeating session/member authorization for every retained row. No grants or write policies are broadened. The initial row-correlated policy timed out with 100,000 entries; the equivalent owner-set trial returned the bounded page in 5 ms in the recorded local diagnostic. That observation is not a hosted capacity guarantee. See [Supabase's RLS performance guidance](https://supabase.com/docs/guides/database/postgres/row-level-security-performance).

The retained local and test installations have `20261023195002_bounded_group_invitations.sql` and `20261023195313_invitation_read_owner_set.sql`. Acceptance covers 100,000 historical entries with cleanup stopped, 100 accepted invitations followed by rate rejection, exact replay, capacity recovery, pruned/stale cursors, unrelated/member/removed-owner denial, stale claims after logout and direct grant/RLS checks. Browser journeys cover bounded navigation, focus, older-link revocation and unchanged private data in Chromium, WebKit and Firefox. Existing controls reflow in English, Russian and Uzbek Latin at 320/375/393/430/1440 px, both appearances and 100/200% text.
